# SourceOS 自治浏览器研究 Agent 设计

> 日期：2026-08-08
>
> 状态：设计已确认
>
> 适用项目：SourceOS 需求到利润经营系统
>
> 核心原则：最大自主、采集优先、全量处理、失败自愈、经验沉淀、人类主要查看结果

## 1. 背景与决策

SourceOS 已经验证了 YouTube、Google Play、Discourse、GitHub 等来源的免费评论采集链路，并在首轮实跑中取得 476 条评论或评测。现有架构也已经具备 FastAPI、PostgreSQL、Redis、RQ、APScheduler、Playwright、yt-dlp、站点适配器和证据模型基础。

新的产品方向不再把浏览器当作官方 API 失败后的低频兜底，而是增加一个拥有持久数字身份、浏览器执行能力、长期记忆和自主规划能力的研究 Agent。用户只提出自然语言需求，Agent 自行定义研究任务、规划来源、登录或注册账号、执行全量采集、完成音视频转写、验证完整性、整理结果，并在有持续价值时建立监控。

单页深采、跨站探索和持续监控不是三个需要用户选择的独立产品：

- 单页深采是最小执行能力；
- 跨站探索是 Agent 对多个执行能力的动态编排；
- 持续监控是带有时间触发器和增量状态的长期研究任务。

系统采用混合路线：Agent 在任务层泛化，底层工具在执行层保持确定。首次进入未知站点时，Agent 可以像人一样观察和探索；成功后应把路径沉淀成可复用、可测试的站点能力。采集正确性和完整性不得只依赖自由生成式判断，必须由确定性的完整性账本和验收器验证。

## 2. 目标与非目标

### 2.1 目标

1. 用户只需表达研究需求，无需预先选择站点、关键词、采集模式或工作流。
2. Agent 自行生成并持续修订任务定义、研究问题、来源计划、证据标准和结束条件。
3. Agent 在信息采集范围内默认自主执行，不因普通登录、页面变化、单一来源失败或执行策略选择而暂停询问。
4. Agent 可以使用已有账号，也可以自行创建邮箱或邮箱别名、注册平台账号、管理密码、验证邮件、TOTP 和持久会话。
5. 对每个被纳入目标的视频采集可访问范围内的全量评论、全量回复、全量弹幕，并完成全部时长的视频转写。
6. Agent 能够跨页面、跨站点、跨语言探索，并根据证据缺口自主扩大或调整研究范围。
7. Agent 能够建立持续监控，完成首次全量基线、后续增量采集和周期性全量对账。
8. 任务、材料、经验和结论同时对 Agent 可检索、对人类可阅读，并能够写入 Obsidian。
9. 长任务支持断点恢复、幂等执行、局部重试和故障路径切换。
10. 系统能够从临场探索中形成站点能力，并在能力漂移时自主回退、修复和升级。
11. 系统首次启动即内置丰富、版本化且可直接选用的采集对象目录，不要求用户从空清单开始。
12. Agent 能够根据自然语言任务从内置目录选择种子目标，并自主发现、补充和维护新的目标。
13. 用户和 Agent 均可通过 YAML、JSON、CSV、OPML、浏览器书签和纯 URL 清单导入或导出自定义采集对象。

### 2.2 非目标

本设计只覆盖浏览、搜索、登录、注册、采集、下载、转写、整理、推理和监控，不包含代表用户发布内容、发送评论或私信、联系外部人员、购买服务或作出商业承诺。这是产品任务边界，而不是对正常采集过程增加人工审批。

平台已经删除、当前账号无权访问、或平台从未返回的内容不属于可验证的全量结果。系统必须如实记录缺口，不得把不可访问内容推断为已采集。

## 3. 自治执行原则

### 3.1 默认自治

在任务范围内，Agent 可以自主：

- 选择平台、来源、语言、关键词和时间范围；
- 打开页面、滚动、点击、展开、搜索和切换入口；
- 使用已有账号、恢复会话或注册新账号；
- 收取验证邮件、提交验证码和管理 TOTP；
- 调用页面、网络响应、公开接口、媒体资源和本地处理工具；
- 改变并发、重试、账号、入口、媒体处理或转写策略；
- 扩展新的来源、对象和研究分支；
- 创建、调整、休眠或终止持续监控；
- 更新任务计划、证据状态和研究结论。

只有确实缺少系统无法自行获得的物理资源，例如必须由真人提供的证件、实体手机或生物识别，且替代路径均已失败时，任务才进入阻断状态。单个目标阻断不得自动中止其他仍可执行的目标。

### 3.2 自主任务定义

用户输入后，Agent 自动建立并版本化任务契约：

```yaml
goal: 用户希望得到的最终结果
actors: 研究对象或相关人群
questions: Agent 拆解的研究问题
source_strategy: 初始来源和扩展方法
languages_and_markets: 初始范围与动态扩展依据
evidence_requirements: 原文、上下文、来源、时间和关系要求
completeness_requirements: 评论、弹幕和转写的全量要求
output_contract: 资料、报告和 Obsidian 输出
completion_conditions: 信息增益、证据覆盖和完整性门槛
monitoring_decision: 是否以及为何进入持续监控
```

任务契约是 Agent 的内部工作契约，不是等待用户批准的表单。每次重要修改都保留修改前后内容和理由。

## 4. 总体架构

系统采用本地优先、控制面与执行面分离的架构。

```text
用户自然语言需求
  -> SourceOS API 与任务控制面
  -> Pi Agent Runtime：理解需求、局部规划、工具选择、评估与重规划
  -> 默认采集目录、自定义 Target Pack 与能力选择
  -> 任务调度
  -> 持久浏览器运行环境
     -> 浏览器扩展：页面、网络、媒体与交互感知
     -> Playwright：浏览器控制与状态恢复
     -> 身份与凭据中心：邮箱、账号、密码、Cookie、TOTP
  -> Redis / RQ Worker
     -> 评论与弹幕采集
     -> 媒体获取与 FFmpeg 处理
     -> 完整转写
     -> 完整性复核
     -> 持续监控与全量对账
  -> PostgreSQL：任务、关系、状态和索引
  -> 本地内容寻址文件库：原始响应、页面、媒体、转写
  -> Obsidian / Markdown：人类可读工作空间和研究报告
```

### 4.1 自治研究 Agent

负责理解需求、定义任务、选择来源、编排能力、判断证据缺口、重规划、决定完成或监控。它不直接承担长时间媒体处理，也不把临场生成的结果当作完整性证明。

### 4.2 浏览器运行环境与扩展

持久浏览器保存页面状态、浏览器档案、登录会话和正在执行的任务上下文。浏览器扩展作为 Agent 的眼睛和手，提供：

- DOM、可访问性树和页面语义；
- 页面截图和视觉状态；
- 网络请求、响应和分页参数；
- 浏览器存储、下载事件和媒体状态；
- 标签页、导航、点击、输入、滚动和播放器控制；
- 操作前后的页面与数据变化。

扩展不保存长期任务真相。即使扩展升级、崩溃或被替换，Agent、任务、身份和证据仍能恢复。

### 4.3 本地处理服务

承担下载、续传、转码、音轨提取、音频切片、语音识别、时间轴合并、字幕解析、弹幕解析、内容哈希和大文件归档。长任务独立于浏览器页面生命周期运行。

### 4.4 能力注册中心

保存通用浏览器能力、确定性站点适配器、Agent 探索形成的成功轨迹、适用条件、验证条件、失败替代和能力健康状态。

### 4.5 证据与记忆中心

保存任务状态、经历、站点方法、研究实体与主张、全部原始材料、规范化内容、转写、证据卡和报告。它既支持机器检索，也投影为人类可读文档。

### 4.6 任务与调度中心

统一处理即时任务、跨站研究、长媒体任务、持续监控、重试、断点恢复和周期性完整对账。

## 5. 自治任务循环

任务状态如下：

```text
received
  -> defining
  -> planning
  -> acquiring
  -> assessing
     -> expanding -> acquiring
     -> recovering -> acquiring
     -> processing
  -> synthesizing
     -> expanding -> acquiring
     -> delivering
  -> monitoring | completed | completed_with_gaps
```

任务可以同时存在多个目标和子任务。单个目标失败时进入 `recovering`，其他目标继续执行。

每轮采集后，Agent 评估：

- 材料是否回答当前研究问题；
- 是否存在单一来源偏差；
- 是否缺少完整上下文、弹幕、字幕或行为证据；
- 哪个平台、语言、关键词和时间范围最可能补齐缺口；
- 继续采集是否仍产生有效信息增益；
- 任务应结束、扩展还是转为长期监控。

默认故障恢复顺序为：

1. 重试当前操作；
2. 重新观察页面和会话状态；
3. 切换 DOM、语义、网络响应或视觉操作方法；
4. 切换账号、入口、关键词或媒体格式；
5. 搜索同一内容的替代来源；
6. 重新设计局部计划；
7. 记录不可恢复缺口并继续其他目标。

## 6. 浏览器探索与能力进化

执行策略按稳定性和效率排序：

```text
已验证站点能力
  -> 通用 DOM / 语义操作
  -> 网络响应和页面状态分析
  -> 视觉识别与人类操作模拟
  -> 替代入口或替代来源
```

未知站点的首次探索可以使用视觉和语义推理。完成目标后，Agent 保存成功轨迹：

```yaml
site: 站点和适用页面类型
goal: 能力完成的原子目标
preconditions: 登录、页面和权限条件
observations: 关键页面、网络和媒体信号
actions: 可重放步骤
postconditions: 成功后的可验证状态
completeness_checks: 数量、分页、时间范围和关系验证
fallbacks: 失败替代路径
fixtures: 用于回放和契约测试的样本
```

成功轨迹经再次运行验证后晋升为站点能力。能力具有版本、成功率、完整率、处理速度、最近验证时间和漂移状态。

当元素、响应结构、数量或完成条件发生异常变化时，系统把能力标记为漂移，回退到探索模式，形成新版本并保留旧版本供比较和回滚。

## 7. 身份、账号与凭据自治

身份系统按以下关系管理：

```text
Agent 主体
  -> 数字身份
     -> 邮箱或邮箱别名
     -> 地区、语言和基础资料
     -> 持久浏览器档案
  -> 平台账号
     -> 用户名、密码和登录方式
     -> 邮箱验证、TOTP 和恢复方式
     -> 权限与健康状态
  -> 持久会话
     -> Cookie、浏览器存储和最近验证时间
```

Agent 可以直接读写完整凭据，不需要逐次人工授权。凭据保存在统一凭据对象中，任务和行为记录通过账号 ID 引用，避免同一密码散落成多份相互冲突的副本。用户可以查看、导出、接管和修改所有身份资源。

自主注册流程：

1. 判断是否已有满足访问要求的账号；
2. 无账号时分析注册页面和必需字段；
3. 选择已有邮箱、创建邮箱别名或注册新邮箱；
4. 生成用户名、密码和必要身份资料；
5. 读取验证邮件并完成验证；
6. 创建并保存 TOTP 或恢复信息；
7. 验证登录和访问能力；
8. 保存账号、浏览器档案和持久会话；
9. 开始采集任务。

账号异常时依次尝试会话恢复、重新登录、邮箱或 TOTP 验证、平台正常恢复流程、切换账号、注册新账号和更换入口。

## 8. 可见记忆与任务工作空间

记忆分为：

- 工作记忆：当前任务状态、下一步动作和未解决问题；
- 经历记忆：重要成功、失败、策略变化和结果；
- 程序记忆：站点操作、采集流程和故障恢复经验；
- 研究记忆：实体、主题、主张、证据、反证和结论；
- 原始证据：网页、评论、弹幕、字幕、音频、视频、截图和响应。

每个任务自动形成工作空间：

```text
missions/<mission-id>/
  README.md
  mission.yaml
  plan.md
  progress.md
  activity.jsonl
  sources.jsonl
  evidence/
  raw/
  media/
  transcripts/
  findings.md
  report.md
  monitor.yaml
```

`README.md` 提供任务概况、覆盖规模、完整状态、主要发现、当前动作和材料入口。`activity.jsonl` 只记录能够帮助继续任务的重要动作和结果，低层点击与调试记录压缩存档，在能力失效或故障复现时使用。

任务执行期间，Agent 定期整合记忆：更新当前状态、保存关键经历、晋升程序记忆、归并研究实体和证据、更新人类可读进度。任务结束后释放临时上下文，但保留原始来源、完整语料、站点能力、身份资源、研究结论、未解决问题和监控条件。

新任务开始前必须检索长期记忆，避免重复创建账号、重复探索站点、重复尝试已知失败路径或忽略已有研究结论。

## 9. 全量评论、弹幕与完整视频转写

### 9.1 “全量”的操作定义

全量指在当前账号权限、页面可见范围和指定时间截点内，取得平台能够正常提供的全部内容，不设置任意 Top-N、页数或时长限制。

完成状态：

- `complete_verified`：平台计数与结束条件均完成验证；
- `complete_best_effort`：已遍历所有可用入口，但存在少量不可解释差异；
- `changing_during_capture`：采集期间持续变化，已形成明确截点快照；
- `partial_recovering`：存在缺页或缺段，系统仍在恢复；
- `partial_blocked`：所有恢复路径失败，缺口已明确记录。

只有前两种状态可称为全量完成。

### 9.2 全量评论

每个目标保存全部一级评论、全部回复、父子关系、置顶和特殊身份、发布时间、互动指标、排序方式、采集时间、原始响应和规范化结果。

结束条件至少包括：分页游标为空或平台明确返回最后一页、连续请求无新增唯一评论、所有已知回复入口已展开。平台声明数量可用时必须与唯一评论数对账。首次扫描结束后执行增量复扫，以形成时间截点一致的完整快照。

### 9.3 全量弹幕

按视频时间轴和平台分段机制获取普通、顶部、底部和高级弹幕，保存文本、出现时间、可用发送时间、颜色、位置、模式、用户标识和原始分段。系统验证所有时间分段连续覆盖，空分段需要二次确认。

平台提供历史弹幕入口时，Agent 默认回溯当前账号可访问的全部历史弹幕，而不是只保存当前弹幕池。只有用户明确限定研究时间范围时，才按该范围形成全量结果。

### 9.4 完整视频转写

对每个纳入目标的视频处理完整时长：

1. 恢复单视频、分 P、剧集和播放列表结构；
2. 获取全部被纳入目标的视频部分；
3. 保存平台字幕和语言版本；
4. 获取完整音轨，无法直接取得时使用正常播放期间的音频捕获；
5. 按时间切片转写，并使用重叠避免分片边界丢字；
6. 合并逐句时间轴；
7. 将所有时间段分类为语音、静音、音乐、噪声或缺失；
8. 对真正缺失或识别失败的片段局部重处理；
9. 输出逐句 JSONL、完整逐字稿和整理稿。

转写完成必须核对媒体时长、音轨时长、已处理时长和转写覆盖。正常静音不得误报为转写缺失，音频缺失也不得被静默忽略。

### 9.5 大规模任务

评论、弹幕、媒体、转写和完整性复核使用独立队列并行处理。任务持续数小时或数天时，系统保存断点并持续更新进度。阶段报告必须显式列出后台仍在执行的全量任务，不得为了快速交付而静默抽样。

## 10. 持续监控与增量研究

Agent 在以下情况下可以自主建立监控：研究对象持续发布、评论仍在增长、主题需要趋势观察、证据不足但未来可能更新、或一次性全量采集后仍有持续价值。

监控契约保存：

```yaml
targets: 页面、账号、频道、视频、搜索或主题
discovery_rules: 新目标发现规则
content_types: 视频、评论、弹幕、字幕和页面变化
cursor_and_watermark: 平台游标与时间水位
schedule_policy: 自适应触发策略
baseline_status: 首次全量基线状态
reconciliation_policy: 周期性全量对账
change_actions: 新内容处理和研究更新方法
retirement_conditions: 失去价值或永久不可访问条件
```

第一次运行建立完整基线。后续运行使用游标、水位和内容指纹采集增量，并定期重新全量对账。

发现新视频后，自动完成元数据保存、完整视频转写、全量评论、全量弹幕、综合分析和监控状态更新。已有视频出现新评论时，采集增量并更新其完整评论快照。

Agent 根据变化速度自行调整频率。热门或突发对象进入 `accelerated`，稳定对象维持正常频率，长期无变化对象进入 `dormant`，来源失效进入 `recovering`，发现新来源进入 `expanded`，永久失效或失去研究价值进入 `retired`。历史材料不会因监控结束而删除。

## 11. 输出与研究整理

交付结果分为四层：

1. 任务总览：覆盖规模、完整性、主要发现、变化和当前动作；
2. 研究报告：问题、情境、替代方案、行为、经济证据、反证和未知；
3. 证据卡：每项发现的支持、反对、可信度和待验证问题；
4. 完整语料：全部评论、弹幕、转写、来源、原始响应和媒体。

全量材料采用分层处理：清洗与去重、上下文恢复、按视频或线程分组、分组提取、跨组比较、证据卡和综合报告。全量语料始终保留，摘要不得覆盖或替代原始材料。

采集量、点赞和情绪强度不自动等同于需求强度。报告区分表达证据、行为证据、经济证据和后果证据，并保留支持与反证。

每项重要判断都必须能回到具体评论及其上下文、弹幕时间点、转写时间点、论坛父级讨论、原始页面和采集时间。引用链为：

```text
报告判断 -> 发现或证据卡 -> 规范化内容 -> 原始响应或媒体
```

持续监控更新报告时保留旧版本，并生成新增材料、判断变化和可信度变化说明。

## 12. 核心数据对象

系统至少包含以下领域对象：

- `Mission`：用户目标与当前任务状态；
- `MissionDefinitionRevision`：Agent 生成的任务契约版本；
- `PlanRevision`：执行计划和修改原因；
- `Target`：页面、账号、频道、视频、搜索或主题目标；
- `SourceCatalogEntry`：平台、入口、访问方式和能力状态定义；
- `TargetCatalogEntry`：可直接执行或实例化的内置采集对象；
- `TargetPack` / `TargetPackVersion`：版本化的内置或自定义采集对象包；
- `TargetListImport` / `TargetListExport`：清单导入、导出、校验和冲突报告；
- `IdentityProfile`：Agent 数字身份和浏览器档案；
- `PlatformAccount`：平台注册身份、权限和健康状态；
- `Credential`：密码、Cookie、令牌、TOTP 和恢复信息；
- `BrowserSession`：持久会话与页面恢复状态；
- `Capability` / `CapabilityVersion`：通用或站点能力及版本；
- `AcquisitionRun`：一次采集运行和分页状态；
- `Artifact`：原始页面、响应、文件或媒体；
- `Comment` / `Danmaku`：规范化评论、回复和弹幕；
- `MediaAsset`：视频、音频、字幕和分段；
- `TranscriptSegment`：带时间戳和质量状态的转写段；
- `CompletenessLedger`：数量、覆盖、缺口和完成依据；
- `Finding`：研究发现与适用情境；
- `EvidenceLink`：发现、规范化内容和原始材料之间的关系；
- `Monitor` / `MonitorRun`：持续监控契约、水位和运行记录。

数据库保存对象状态和关系，大型内容保存到本地内容寻址文件库。所有文件使用内容哈希避免重复，并通过 Artifact ID 与数据库关联。

## 13. 故障恢复与完成证明

故障按浏览器、身份、站点、网络、媒体、转写、存储、Agent 推理和质量分类。所有长任务必须支持：

- 分阶段检查点；
- 分页游标和时间水位；
- 媒体分段续传；
- 转写片段状态；
- 内容哈希和唯一标识；
- 幂等写入；
- 进程重启后自动续跑。

系统检测动作是否产生新页面状态、数据或任务状态。连续重复而无进展时，停止当前动作并升级策略，避免 Agent 无限循环。

任务只有同时满足以下条件才进入 `completed`：

```yaml
plan: 所有计划目标已处理
comments: 所有必需目标均为 complete_verified 或 complete_best_effort
danmaku: 所有必需目标均为 complete_verified 或 complete_best_effort
transcription: 完整时间覆盖验证通过
evidence: 重要判断可追溯
memory: 任务状态和可复用经验已整理
report: 人类可读结果已生成
monitoring: 已建立监控或明确判定无需监控
```

仍有目标在恢复时使用 `delivering_partial`、`recovering` 或 `monitoring`，可以交付阶段结果，但不得标记全部完成。所有替代路径均失败且仍存在不可恢复缺口时使用 `completed_with_gaps`；该状态表示系统已经停止继续尝试并交付了可得结果，不表示满足全量要求，也不得在界面或报告中显示为“全量完成”。

## 14. 测试策略

测试分为六层：

1. 单元测试：分页、去重、父子关系、时间轴、状态迁移和完整性计算；
2. 站点契约测试：固定页面和响应样本验证适配器；
3. 回放测试：重放真实页面、网络响应和媒体状态；
4. 浏览器端到端测试：在真实目标上完成一次采集；
5. 故障注入测试：断网、浏览器崩溃、登录过期、重复页和媒体缺段；
6. 长期漂移测试：周期性检查站点能力是否仍满足契约。

关键验收场景：

- 任意分页位置关闭系统后准确续跑；
- 评论持续变化时形成一致的时间截点快照；
- 重复分页响应不会造成无限循环或重复数据；
- 登录失效后 Agent 自主恢复或切换账号；
- 页面结构变化后能力自动回退到探索模式；
- 视频中间缺少音轨时能够发现并局部重处理；
- 更换转写模型后时间轴仍能合并；
- 监控增量能够并回完整快照，并由周期全量对账验证；
- Agent 和 Worker 完全重启后能够恢复当前任务；
- 报告中的每个证据引用都能返回真实材料。
- 内置目录中目标 ID 唯一，软件升级后稳定 ID 和本地自定义包不被覆盖；
- YAML 与 JSON 清单完成导出、重新导入和语义等价比较；
- Pi Runtime 中途退出后，SourceOS 能依据 PostgreSQL 任务状态恢复，并且不会重复派发已有 RQ Job 或重复执行已完成的外部动作；
- 删除 Pi 的临时消息或单次 Run 状态后，SourceOS 中的任务、目标、证据和长期记忆仍然完整；
- 未知站点能够由 Pi 通过 Playwright、浏览器扩展和通用观察/动作工具自主探索，成功路径能够沉淀为确定性站点能力。

## 15. 建设顺序

建设顺序表达技术依赖，不削减单页深采、跨站探索和持续监控中的任何一项。

### 15.1 里程碑一：完整纵向闭环

以 Bilibili 和 YouTube 为首批参考站点，实现：

```text
自然语言需求
  -> Agent 自主定义和规划
  -> 跨两个平台寻找目标
  -> 单目标全量评论
  -> Bilibili 全量弹幕
  -> 视频完整转写
  -> 完整性验证
  -> Obsidian 输出
  -> 自动建立监控
  -> 增量更新材料和结论
```

该里程碑必须同时证明单页深采、跨站探索和持续监控，并支持持久浏览器、已有账号登录、任务记忆和中断恢复。

里程碑一同时交付默认采集对象目录和清单导入导出闭环。Agent 必须能够从默认启用的核心种子包选择 Bilibili、YouTube 及其他相关目标，也必须能够导入一份用户 URL 清单、执行规范化去重、将其用于同一任务，并无损导出为 YAML 和 JSON。

### 15.2 里程碑二：身份完全自治

实现邮箱读取、邮箱别名、平台注册、密码与 TOTP 管理、账号恢复、多身份选择和缺少账号时的自主创建。

### 15.3 里程碑三：未知站点自主泛化

实现未知页面观察、DOM / 网络 / 视觉探索、成功轨迹保存、重复验证、能力晋升、漂移检测和自主修复。

### 15.4 里程碑四：全域规模化

实现多浏览器 Worker、大规模媒体队列、多模型转写、跨平台去重、实体归并、自适应监控、存储归档和数百目标长任务对账。

### 15.5 里程碑五：长期自我进化

系统依据真实运行的成功率、完整率、处理速度、恢复能力和单位资源消耗，自主决定能力选择、站点维护优先级、监控频率和模型策略。

## 16. 第一完整里程碑的验收标准

第一完整里程碑通过以下场景验收：

1. 用户只输入一段自然语言研究需求；
2. Agent 自行形成任务定义、来源计划和完成条件；
3. Agent 在 Bilibili 与 YouTube 上自主寻找相关视频；
4. 至少一个 Bilibili 目标完成全量评论、全量回复、全量弹幕和完整视频转写；
5. 至少一个 YouTube 目标完成全量评论、全量回复和完整视频转写；
6. 每个目标均产生完整性账本和原始材料；
7. 任务中途强制重启后能够自动续跑；
8. Agent 生成 Obsidian 可读的总览、完整逐字稿、证据卡和报告；
9. Agent 自行建立监控，并在测试新增内容后完成增量采集；
10. 增量结果能够并回完整快照，报告生成变化说明；
11. 用户能够从报告判断跳回具体评论、弹幕时间点和转写时间点；
12. 除无法自行获得的物理验证资源外，整个流程无需人工逐步操作。
13. 系统已导入现有 203 项来源注册表，并能区分来源能力、采集对象和采集对象包；
14. 至少 12 个内置 Target Pack、250 个内置目标模板和 40 个默认启用核心种子目标可被 Agent 检索；
15. 默认启用目标覆盖至少 12 个平台、6 类信号和中英文两种语言环境；
16. 一份包含 URL、频道、搜索、仓库和播放列表的自定义清单能够完成导入预检、规范化、去重、执行和导出回环；
17. YAML 与 JSON 导出后重新导入，除运行状态和导出时明确排除的字段外，目标语义保持一致。

## 17. 默认内置采集对象目录

### 17.1 三层目录模型

系统必须区分三种对象，避免把“登记了很多站点”误认为“已经拥有丰富的可运行目标”：

```text
SourceCatalogEntry
  平台及入口能力，例如 YouTube、Bilibili、GitHub Issues
    -> TargetCatalogEntry
       具体频道、账号、社区、仓库、应用、视频、播放列表或搜索模板
         -> TargetPack
            面向某类研究任务的版本化目标集合
```

现有 `source_registry.json` 中的 203 项来源全部迁移到 `SourceCatalogEntry`，保留访问状态、优先级、连接器和实现状态。它们是来源能力底座，不直接计入可执行采集对象数量。

### 17.2 内置目标类型

内置目录至少支持：

- 具体页面或 URL；
- 视频、分 P、剧集和播放列表；
- 频道、创作者、账号或组织；
- 评论线程、论坛社区和主题板块；
- 搜索关键词、组合查询和趋势页；
- GitHub / GitLab 仓库、Issue 和 Discussion；
- 应用、插件、游戏、商品和评价页；
- RSS、播客节目和音频专辑；
- 产品发布、众筹、采购、资助和竞赛目录；
- 本地文件、已有书签和 Obsidian 中保存的外部链接。

每个条目至少包含：

```yaml
target_id: 稳定唯一标识
kind: channel | account | video | playlist | community | query | repository | app | feed | url
platform: 平台标识
locator: 规范 URL、平台 ID 或查询定义
title: 人类可读名称
languages: 语言列表
markets: 地区列表
signal_types: 评论、弹幕、问题、评价、发布、采购等
acquisition_policy:
  comments: full
  replies: full
  danmaku: full_when_available
  transcription: full_when_media
monitor_policy: 默认监控策略
capability_state: discovered | verified_executable | browser_explorable | registered_only | temporarily_broken | retired
tags: 主题和用途标签
provenance: 内置、用户导入或 Agent 发现
```

### 17.3 首发内置 Target Pack

首发至少内置以下 12 个包：

1. 中国视频与公开讨论：Bilibili、抖音、快手、西瓜视频等；
2. 全球视频与直播：YouTube、TikTok、Twitch、Vimeo 等；
3. 播客与长音频：小宇宙、Apple Podcasts、Spotify、RSS 播客等；
4. 开发者问题与开源生态：GitHub、GitLab、Gitee、Hugging Face、npm、PyPI 等；
5. 论坛与问答社区：Reddit、Hacker News、Discourse、V2EX、Stack Exchange、知乎等；
6. 应用、插件与游戏评价：Google Play、Apple App Store、Chrome、VS Code、WordPress、Steam 等；
7. 社交平台公开信号：X、微博、小红书、Bluesky、Mastodon 等；
8. 产品发布与独立开发：Product Hunt、Show HN、Indie Hackers、BetaList 等；
9. 众筹与预售验证：Kickstarter、Indiegogo、Makuake、Wadiz、摩点及区域众筹站；
10. 商品、服务与软件评价：电商评价、G2、Capterra、Trustpilot、AlternativeTo 等；
11. 采购、资助、外包与竞赛：SAM.gov、TED、UNGM、Grants.gov、Devpost、Kaggle 等；
12. 论文、专利、标准与技术转移：arXiv、OpenAlex、Crossref、WIPO、USPTO、IETF 等。

首发目录最低包含 250 个内置目标模板，其中至少 40 个组成默认启用的核心种子包，覆盖至少 12 个平台、6 类信号和中英文环境。默认启用表示 Agent 在任务规划时优先检索和选择，不表示系统启动后不加区分地立即采集全部目标。

### 17.4 Agent 自主维护目录

Agent 可以从任务执行中发现新频道、账号、社区、搜索词、播放列表和站点入口。新目标先进入 `discovered` 候选队列；完成规范化、重复检查和一次真实探活后，晋升为自定义 Target Pack 的正式成员。持续成功的高价值目标可以进入核心种子包的新版本，长期失效目标降级但保留历史引用。

内置包只读并按版本升级。用户和 Agent 对内置包的修改通过“克隆为自定义包”完成，避免软件升级覆盖本地选择。

## 18. 自定义清单导入与导出

### 18.1 支持格式

系统必须支持：

- YAML：首选的可读、可版本控制完整格式；
- JSON：无损机器交换格式；
- CSV：适合表格编辑的扁平目标清单；
- OPML：RSS 和播客订阅迁移；
- Netscape Bookmark HTML：浏览器书签导入导出；
- Markdown：提取链接、标题、标签和 Obsidian 上下文；
- TXT：每行一个 URL、平台 ID 或搜索表达式；
- ZIP Bundle：目标清单、JSON Schema、说明文档和可选运行状态的完整包。

### 18.2 导入流程

```text
上传或指定文件
  -> 格式识别与 Schema 校验
  -> URL、平台 ID 和查询表达式规范化
  -> 平台与目标类型识别
  -> 内部重复和现有目录重复检查
  -> 能力可用性与首次探活
  -> 预览新增、更新、跳过和错误项
  -> append | merge | replace 模式执行
  -> 生成导入结果与失败原因
```

Agent 可在无人值守任务中自行导入清单并采用默认 `merge` 策略。无法识别的 URL 不丢弃，保存为通用 `url` 目标并交给浏览器探索。冲突默认以稳定目标 ID、平台原生 ID和规范 URL 判断；同一目标的用户字段优先，运行状态按最新成功记录合并。

### 18.3 导出流程

导出可以选择：

- 单个目标、一个 Target Pack、当前任务目标或全部目录；
- 只导出定义，或同时导出监控水位、能力状态和最近运行摘要；
- 完整格式，或面向 CSV、OPML、书签的兼容子集；
- 当前版本，或指定历史版本。

目标清单只引用 `identity_profile_id` 或账号别名，不把密码、Cookie 和令牌混入目标交换文件。身份资源需要迁移时使用独立的身份资源导出流程，避免目标定义与运行环境绑定。

### 18.4 版本与回环保证

每个导出包包含 Schema 版本、目录版本、生成时间、条目数量、内容哈希和来源说明。YAML 与 JSON 必须满足导出后重新导入的语义回环：目标类型、定位符、采集策略、监控策略、标签和包关系保持一致。CSV、OPML、书签和 TXT 属于有损兼容格式，导出时明确列出无法表达的字段。

导入导出同时提供 API、CLI 和界面入口。所有导入先产生预检报告，Agent 可以自行继续执行；人类也可以查看并修改预检结果。

## 19. Pi Agent 框架选型

完整的一手资料修正见：[SourceOS Pi Agent 框架修正调研](../../technical-design/2026-08-08-pi-agent-framework-correction-research.md)。

### 19.1 选型结论

认知执行内核采用：

```text
@earendil-works/pi-agent-core
  + @earendil-works/pi-ai
```

浏览器执行层采用：

```text
Pi Agent
  -> SourceOS Browser Tools
     -> Playwright
     -> SourceOS 浏览器扩展
     -> 确定性站点能力
```

不引入额外的图编排框架或第二套浏览器 Agent 框架。Pi 直接通过 SourceOS 提供的浏览器观察、动作、网络检查和采集工具探索未知站点；成功路径由 SourceOS 能力注册中心固化。

选择 Pi 的原因：

1. `pi-agent-core` 是小型、可嵌入的有状态 Agent 循环，提供工具执行、参数 Schema、流式事件、上下文变换、中止、转向和追问队列，不要求业务迁就预设图或多角色模型。[Pi Agent Core README](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)
2. `pi-ai` 提供多模型接入、流式输出和工具调用，模型供应商可以替换，不需要再引入大型 Agent 生态。[Pi 官方仓库](https://github.com/earendil-works/pi)
3. Pi SDK 明确支持嵌入现有应用、自定义界面、自动化工作流和自定义工具，符合 SourceOS 将其作为执行内核而非产品控制面的方式。[Pi SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)
4. SourceOS 原有产品定义、技术 Issue 和技术方案已经采用 Pi；继续使用同一运行时保持架构连续性，避免同时维护两套 Agent 抽象。
5. Pi 保持极简，长期任务可靠性继续由 SourceOS 的 PostgreSQL、RQ 和 APScheduler 提供，而不是为获得 checkpoint 再引入一整套框架。

### 19.3 SourceOS 与 Pi 的边界

Pi 负责：

- 理解当前任务和阶段目标；
- 生成或修订局部计划；
- 选择并调用 SourceOS 工具；
- 根据工具结果继续、转向、追问或结束当前 Run；
- 发现证据缺口、选择新目标和提出恢复策略；
- 通过浏览器工具探索未知站点；
- 通过事件流报告思考回合、工具执行和结果。

SourceOS 始终负责：

- 用户需求、Mission 状态机和任务契约版本；
- 默认目录、自定义清单、来源、目标和 Target Pack；
- 评论、弹幕、媒体、字幕、逐字稿和原始材料；
- 完整性账本与 `completed` 判定；
- 账号、邮箱、凭据、浏览器档案和持久会话；
- 站点能力、成功轨迹、版本和漂移状态；
- RQ Job、重试、租约、幂等、超时和资源队列；
- APScheduler 监控触发器、游标和水位；
- 长期研究记忆、证据关系和 Obsidian 文档。

Pi 的进程内消息、`sessionId` 或单次 Agent 状态都不是 SourceOS 的业务事实源。Pi Run 丢失后，系统必须能够从 PostgreSQL 中的 Mission、Operation、Job、Artifact 和 Memory 记录恢复。

### 19.4 轻量接入方式

SourceOS 保持 Python / FastAPI 主控制面，增加一个隔离的 TypeScript Runtime Adapter：

```text
SourceOS Python Control Plane
  -> AgentRuntimePort
  -> PiSubprocessAdapter（首版）
     -> @earendil-works/pi-agent-core
     -> @earendil-works/pi-ai
  -> JSONL 事件与工具协议
  -> SourceOS Tool Gateway
  -> PostgreSQL / RQ / Browser Runtime / File Store
```

领域层只依赖 SourceOS 自己的 `AgentRuntimePort`、`AgentRunEnvelope`、`AgentEvent` 和 `AgentToolResult`，不得直接依赖 Pi 类型。首版使用 Node 子进程和 JSONL 协议降低部署复杂度；需要更高吞吐时可以替换为常驻 Pi Worker，而不改变业务对象和工具契约。

首版只采用 `pi-agent-core` 和 `pi-ai`。`pi-coding-agent` 可以作为源码和会话管理参考，但不作为 SourceOS 业务控制面，避免带入不需要的编码工具、CLI 和项目约定。

### 19.5 不使用图框架的耐久任务循环

长期任务由 SourceOS 自有 PostgreSQL 状态机驱动：

```text
received
  -> defining
  -> planning
  -> acquiring
  -> assessing
     -> recovering -> acquiring
     -> expanding -> acquiring
     -> processing
  -> synthesizing
  -> monitoring | completed | completed_with_gaps
```

每次调度只创建一个可恢复的 `AgentRun`：

1. SourceOS 从数据库读取 Mission、当前阶段、目标 ID、Job ID 和证据缺口；
2. 构造有限的 `AgentRunEnvelope`，交给 Pi；
3. Pi 自主调用工具，直到当前阶段目标完成、需要等待异步 Job 或遇到不可恢复阻断；
4. SourceOS 订阅 Pi 事件并持续写入工作记忆和 Run 状态；
5. 工具通过事务写入业务结果，并返回稳定 ID；
6. Run 结束后，SourceOS 根据确定性结果迁移 Mission 状态；
7. 需要继续时，由 RQ 完成事件、APScheduler 或数据库中的下一运行时间触发新的 Pi Run。

因此，Pi 负责“这一回合应该做什么”，SourceOS 负责“任务现在真实处于什么状态、如何恢复和何时再次运行”。

### 19.6 Pi 浏览器工具集

第一批工具至少包括：

- `search_target_catalog`：搜索默认和自定义采集对象；
- `import_target_list` / `export_target_list`：管理目标包；
- `browser_observe`：读取页面语义、截图、标签页和关键状态；
- `browser_navigate` / `browser_act`：导航、点击、输入、滚动和播放器控制；
- `browser_inspect_network`：检查页面请求、响应、游标和媒体信息；
- `collect_full_comments`：派发全量评论和回复任务；
- `collect_full_danmaku`：派发全量弹幕任务；
- `transcribe_full_media`：派发完整媒体转写任务；
- `read_job_status`：读取 RQ Job 和完整性账本；
- `register_site_capability`：保存并验证成功路径；
- `schedule_monitor`：建立或修改持续监控；
- `retrieve_evidence`：按 ID 和查询读取有限证据；
- `write_mission_memory`：更新任务工作记忆和下一步摘要。

Pi 面对未知站点时先调用通用浏览器工具探索；已有站点能力存在时优先调用确定性工具。模型不直接声明“已经全量”，只能读取 SourceOS 完整性验收器的结果。

### 19.7 幂等、恢复与状态大小

每个产生外部动作的工具必须接收：

```text
mission_id
target_id
operation_type
idempotency_key
attempt_id
```

SourceOS 在执行前查询 Operation 表和浏览器后置状态。相同幂等键已经成功时返回既有结果；仍在运行时返回 Job ID；失败可恢复时创建新 attempt。Pi Run 重试不得造成重复下载、重复注册、重复评论写入或重复监控。

传给 Pi 的上下文只包含必要 ID、摘要、当前计划和有限证据片段。全量评论、弹幕、HTML、媒体和逐字稿保存在 SourceOS 中，由 `transformContext` 和检索工具按需加载，避免 Agent 消息随资料规模线性膨胀。

### 19.8 升级与替换

Pi 通过 Adapter 隔离，升级必须通过以下契约测试：

- Agent 事件顺序和结束语义；
- 工具参数校验、并行和顺序执行；
- `beforeToolCall` / `afterToolCall` 行为；
- abort、continue、steer 和 follow-up；
- 模型切换与上下文转换；
- 子进程退出与 Run 恢复；
- 工具幂等和 RQ Job 不重复派发；
- 浏览器探索轨迹和站点能力沉淀。

如果未来替换 Pi，SourceOS 的 Mission、Target、Artifact、CompletenessLedger、Monitor 和长期记忆无需迁移，只替换 `AgentRuntimePort` 的实现。

## 20. 设计结论

SourceOS 应新增一个以 Pi 为认知执行内核的自治浏览器研究运行时，而不是只新增一个浏览器采集插件。插件负责浏览器环境中的感知与执行；Pi 负责任务理解、局部规划、工具选择和重规划；SourceOS PostgreSQL 状态机负责长期任务事实与恢复；确定性能力负责可重复执行和完整性验证；本地 Worker 负责媒体与长任务；证据和记忆系统负责恢复、复用与人类可见。

系统的核心产品承诺是：用户提出需求，Agent 自主管理身份和浏览器，自行完成全量采集、完整转写、跨站探索、持续监控和研究整理，并把全部材料与结论以可追溯方式交付到 SourceOS 和 Obsidian。
