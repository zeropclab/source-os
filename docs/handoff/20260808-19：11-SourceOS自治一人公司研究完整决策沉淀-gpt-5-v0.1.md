# SourceOS 自治一人公司研究完整决策沉淀

## 1. 文档目的

本文用于把本轮长期对话中形成的产品定位、反对意见、架构判断、领域概念、自治边界、自我进化机制和建设顺序完整沉淀到 SourceOS 项目中，供另一台主机和后续 Agent 继续工作。

本文不是逐字聊天导出，而是按时间与因果关系整理的完整实质内容。它保留了所有会改变产品方向的用户观点、反驳、修正、已接受决定和未解决矛盾，避免迁移后只看到结论而不知道结论为什么成立。

配套交接文件：[[20260808-19：11-SourceOS跨主机研究开发交接手册-gpt-5-v0.1]]。

## 2. 最初问题与长期目标

最初目标是通过全球评论、讨论和公开材料发现现实需求：收集大量评论，恢复上下文，识别现实中的人群、场景、痛苦、替代行为和未满足结果，并据此定义能够创造真实价值的产品或服务。

用户明确要求：

- 不局限于婚恋或任何单一领域；
- 面向海外、一带一路、全球南方、中东、中亚、南美、非洲、发达国家，以及越南、墨西哥、波兰、印度尼西亚、巴西等不同市场；
- 系统首先服务用户本人，而不是面向公众；
- 用户当前是上班族，可投入时间大约每天两小时；
- 用户尚未真正完成过一个经过投放、销售、交付、留存和复购验证的产品；
- 核心短板是缺少现实信息、渠道、需求接触、销售与交付经验；
- 长期目标是成为能够盈利、养家糊口并持续积累能力的独立开发者和一人公司。

因此，SourceOS 的价值不能被定义为“生成更多想法”或“输出更漂亮的研究报告”，而必须服务于有限时间和资源下的更好产品下注。

## 3. 从“寻找最痛苦的人”到现实需求判断

早期产品定义使用“谁最痛苦、最痛苦什么”作为需求入口。讨论后形成修正：痛苦可以是重要信号，但不能等同于产品需求。

原因包括：

- 强烈表达不等于愿意付费；
- 评论者可能不是购买者；
- 高痛苦问题可能无法被产品解决；
- 问题真实但人群不可触达，仍然不是个人开发者的商业机会；
- 有人从不抱怨，却持续支付高额时间或金钱成本解决问题；
- 评论密集可能来自同一传播链，而不是独立需求。

需求判断必须结合：

- 目标主体与发生场景；
- 可观察行为；
- 时间、金钱、风险和机会成本；
- 重复性替代方案；
- 现有购买和采购行为；
- 竞品采用、流失、退款与差评；
- 可触达渠道；
- 产品干预能否改变行为；
- 使用、留存、付费和复购结果。

最终从“痛苦挖掘”升级为“多源现实证据驱动的需求判断”。

## 4. 评论采集是否能够发现真实需求

结论：可以成为重要入口，但不能单独完成需求验证。

评论能够帮助发现：

- 用户如何描述问题；
- 问题发生的具体上下文；
- 反复失败的工作流；
- 自制表格、脚本、人工服务等替代行为；
- 现有产品缺陷；
- 弱信号、异常案例和跨领域结构；
- 语言、地区和人群之间的相似机制。

评论不能单独证明：

- 总体市场规模；
- 支付意愿；
- 用户可触达性；
- 具体产品会被采用；
- 产品能够留存和复购；
- 获客成本和单位经济成立。

因此，采集对象需要从评论扩展到视频、弹幕、转写、论坛上下文、应用评价、搜索趋势、众筹预售、采购、招聘、外包、竞品定价、交易和产品经营结果。

## 5. 本体论与隐性需求空间

本体论被接受为发现隐性空间、弱关联和交叉领域需求的重要方法，但不能被当作自动产生真需求的机器。

需要建模的核心对象包括：

- Actor；
- Context；
- Trigger；
- Problem；
- Constraint；
- Behavior；
- Workaround；
- Cost；
- Consequence；
- Desired Outcome；
- Evidence；
- Counterevidence；
- Mechanism；
- Intervention；
- Result。

跨领域泛化应寻找机制同构，而不是简单关键词相似。例如，不同国家和行业中表面不同的问题，可能都源于现金流不确定性、信任成本、身份验证摩擦或信息不对称。

同时确认了本体论的风险：对象和关系越多，系统越容易发现看似新颖但实际虚假的关联。因此关系必须区分：

- 直接观察关系；
- 统计关联；
- 模型推断关系；
- 待验证机制；
- 因果假设；
- 已观察干预结果。

新关联必须经过重复性、机制、反例和行动价值过滤。

## 6. 通用智能体与 SourceOS 的存在性问题

讨论直接挑战了 SourceOS 是否有必要独立开发。结论是：如果 SourceOS 只是让大模型搜索、总结评论并生成产品想法，就没有独立开发价值。通用智能体已经能够完成多步研究、项目记忆、应用连接、定时任务和带引用报告。

SourceOS 可能成立的差异不在模型智力，而在以下四点：

1. **权威事实**：原始材料、证据候选、已接受证据、解释、判断、Proposal、正式需求、决策和结果是不同对象。
2. **强制协议**：Agent 不能靠语言承诺遵守规则，系统必须阻止无证据提升、重复信号冒充独立证据和越权操作。
3. **长期反馈**：保存证据—判断—产品—经营结果的纵向关系，让成功和失败改善后续判断。
4. **跨模型复利**：模型可替换，数据、领域协议、决策历史、能力谱系和评测结果属于用户。

形成的核心表达：

> 通用智能体负责思考，SourceOS 负责让思考不能胡来、不能失忆、不能伪造进展，并让正确和错误都成为下一次判断的资产。

SourceOS 不是一场持续数月的模型会话，而是长期状态机协调的一系列短周期、有边界、可恢复的 Agent Run。

## 7. 从需求发现到产品干预预测

产品价值被进一步提升为：在开发之前，用现实数据降低产品下注的不确定性，提高有限资源的配置质量。

系统预测的不能只是“需求是否存在”，而是：

> 在明确人群、场景、产品形式、价格、渠道、资源和时间条件下，采取某项产品干预后产生目标行为与经营结果的可能性。

产品成功概率应拆解为条件链：

- 问题是否真实；
- 目标人群是否可识别和触达；
- 产品干预是否能改变行为；
- 用户是否愿意付费；
- 是否持续使用；
- 单位经济是否成立；
- 当前执行者是否能交付。

形成的新对象是 `Product Intervention Thesis`，它不同于 `Need Hypothesis`：前者回答“我们这样介入是否可能改变现实”，后者只回答“问题是否真实”。

预测必须有明确时间、目标和资源条件。例如：未来九十天、每天两小时、指定预算和渠道、达到明确付费与留存指标。没有这些条件，“产品会不会成功”不可证伪。

早期不能输出伪精确概率。应先输出风险向量、概率区间、证据等级、关键假设、致命风险和下一项最有信息价值的行动。形成足够历史结果后，再用事前预测与真实结果校准。

## 8. SourceOS 的科学边界

多轮大模型推演不会自动产生新证据。同一模型分析同一批材料十次，可能只会产生更连贯的错误故事。

因此需要角色和方法分离：

- 观察者只提取可见事实；
- 分类器识别人群、场景、行为和成本；
- 谱系分析器判断来源独立性；
- 反证 Agent 主动寻找推翻条件；
- 机制分析器构建解释；
- 产品 Agent 构造干预；
- 商业 Agent 分析价格、渠道和单位经济；
- 校准 Agent 比较历史预测与结果；
- 对抗审查者尝试推翻最终判断。

多 Agent 的价值是扩大假设空间和发现漏洞，不是通过多数票证明事实。使用同一模型、同一数据和相似 Prompt 的多个 Agent 判断高度相关，不能视为独立验证。

## 9. 信息价值与采集原则

数据量不等于有效信息量。一百万条同源复述可能不如一条带采购金额、真实替代成本和上下文的材料。

采集应优化有效信息增益：

> 下一项采集优先级 = 改变当前决策的可能性 × 决策经济影响 ÷ 获取成本。

最终接受的采集原则是：

> **自适应广度＋正式目标内全量深采。**

含义是：

- 来源范围根据研究目标、证据缺口和信息价值自主扩展；
- 不要求全网无差别全量采集；
- 某个视频、线程、应用评价页或社区一旦正式纳入证据范围，就尽可能采集当前权限和时间截点内的全部材料；
- 全量必须有完整性账本和明确缺口，不能由模型自行宣称；
- 采集结果不是评论文件，而是带上下文、谱系、独立性、完整性和版本的 `Reality Dataset`。

`Reality Dataset` 至少包含：原始材料、规范化内容、作者与父子关系、时间、来源与访问方式、完整性、重复与传播谱系、语言地区人群场景、行为与经济信号、实体关系和变化历史。

## 10. 思维连续性与“认知湍流”

“思考摩擦”被重新表述为“推理流动失稳”或通俗的“认知湍流”。它描述长链推理中主线推进、局部探索和逻辑校验失去同步，导致未决事项扩大、反复折返、认知耗竭和主线中断。

这一概念对 SourceOS 的影响包括：

- Objective 主线必须持续可见；
- 支线、未知项、反例和临时 Proposal 需要寄存而不能丢失；
- 无证据主张、缺失上下文和未处理反例形成逻辑债务；
- 中断后应通过检查点快速恢复；
- Legal Next Step 的职责之一是防止无目的采集和推理失稳；
- 不保存模型私有思维链，只保存可审计的事实、主张、未知项、决定和下一步理由。

## 11. 既有 SourceOS Agent-native 架构决定

当前 v1.1 决策地图已经锁定：

- 以 `Discovery Objective Workspace` 为主界面和聚合入口；
- 持久生命周期保持 `active / pending_approval / blocked / completed`；
- Workspace Operational State 由事实派生，不重复持久化；
- Legal Next Step 由纯函数显式优先级决策表产生；
- 输出稳定规则 ID、状态、合法命令、解释和评估轨迹；
- 命令执行时重新校验 Objective 和 Boundary 版本；
- Agent 只产生不可变 `Agent Proposal`；
- 人工提升后才形成正式 Plan Revision、Assessment 或 Need Hypothesis；
- 达到停止条件只产生 `Closure Decision Required`，不能自动宣布需求成立；
- 架构采用 Agent-native 模块化单体，不采用微服务和通用规则引擎；
- Discovery Orchestrator 掌握确定性权威；
- Discovery、Acquisition、Productization 模块独占各自写模型；
- API、worker、模板和 Agent 不能直接修改其他模块 ORM 状态；
- Agent Work 和 Acquisition Work 是持久异步任务；
- Workspace 首版为实时投影，不建立重复 read model；
- FastAPI、SQLAlchemy、Alembic、PostgreSQL、Jinja、自定义 CSS、HTMX、Alpine.js 和 SSE 构成首版 Web 栈；
- Pi 是可替换认知适配器，不是业务事实源。

## 12. 持久化模型讨论尚未完成

数据模型票已经开始，但未完成。当前发现的实际问题包括：

- `ExternalSignal` 同时存在直接 `mission_run_id`、运行中的 `external_signal_ids` 和关联表，事实重复；
- Signal 当前状态与 `SignalTriageEvent` 同时表达分诊状态，可能冲突；
- `AgentRun` 混合逻辑任务、执行尝试、模型输出和人工修改；
- Objective 等可变根缺少统一 `row_version`；
- 幂等只在局部存在，未形成统一命令协议；
- JSONB 快照与权威事实的边界尚不清楚。

已经提出但尚未在 GitHub 票中正式落定的总原则：

> 使用“事务状态表＋不可变事实记录”的混合持久化，不做全量事件溯源，也不采用纯可变 CRUD。

建议方向：聚合根保存当前状态和乐观锁；Boundary、Plan、Proposal、Assessment、Decision、Evidence 和执行结果使用不可变版本或追加记录；命令使用统一幂等键和事务 Outbox；Workspace 与 Legal Next Step 实时派生。

## 13. 从垂直需求 Agent 到自治一人公司

用户提出进一步愿景：理解生产关系、成本管理和利润管理，构建需求发现、战略、商业模型、研发、生产、销售、创作、运营、金融、数据、CEO 和迭代引擎，形成帮助个人盈利的一人公司基础设施。

最终定位从“垂直需求发现 Agent”升级为：

> **SourceOS 是一个受经营宪法约束、以现实结果为选择压力、能够自主感知、决策、生产、经营和进化的控制论一人公司。**

不是多个聊天机器人的集合，而是一套数字生产关系：

- 数据、账号、渠道、代码、模型、能力和品牌是生产资料；
- Agent、确定性工具和自动化设施是数字生产力；
- 目标契约、能力权限、资源、成本、委托、验收和收益反馈是生产关系；
- 产品、客户价值、经营资产和自由现金流是生产结果；
- CEO Engine 负责机会组合和资源配置，不亲自完成所有工作；
- Evolution Kernel 负责变异、实验、评测、选择、提升和回滚；
- 用户保留宪法权、资产权和终止权。

## 14. 最小经营宪法

用户选择探索“完全自我进化”，但接受必须保留极少数不可自行改写的经营宪法。

已接受原则：

1. 引擎可以修改 Prompt、模型、工具、流程和代码；
2. 可以创建、竞争和淘汰子智能体；
3. 可以在隔离环境中自主实验；
4. 不能删除失败事实和审计历史；
5. 不能同时修改实现和评分标准后自行宣布胜利；
6. 长期盈利与生存目标、资源上限、人工终止权属于宪法；
7. 默认允许无资金消耗、可审计、可停止、可回滚的行动；
8. 资金、重大外部承诺、不可恢复资产操作和宪法修改保留所有者授权。

全局适应度不能只使用营收或利润，应按层级考虑：

- 生存与不可承受风险；
- 长期自由现金流；
- 单位经营者时间收益；
- 客户价值持续性；
- 数据、代码、渠道、品牌和流程资产复利；
- 未来选择权。

每个引擎只能优化局部指标，但必须受全局经营适应度约束。

## 15. 三类自我迭代

自我迭代被定义为 SourceOS 的公共基础能力，而不是某一个 Agent 的附属功能。

### 15.1 探索自我迭代

在单次任务中根据证据缺口自主修改问题、查询、来源、语言、地区、目标、深采范围、反证方向和结束条件。

### 15.2 能力自我迭代

跨任务改进浏览器轨迹、站点适配器、工具、模型、Prompt、分类器、完整性检查、预测方法和恢复策略。

### 15.3 产品自我迭代

根据使用、成本和经营结果修改 SourceOS 自身的流程、界面、模块、数据模型和产品能力。

三类迭代共用 `Evolution Kernel`：

```text
观察结果
→ 识别改进机会
→ 生成多个变体
→ 隔离运行
→ 历史回放和真实小流量评测
→ 比较质量、成本与经营结果
→ 提升胜者
→ 持续监控
→ 异常回滚
```

评测器可以提出改进，但参赛版本不能自行修改最高评价标准并批准自己。

## 16. 自治浏览器研究 Agent 的位置

新文档 `2026-08-08-autonomous-browser-research-agent-design.md` 定义了自治浏览器研究 Agent，包括持久浏览器、身份、跨站探索、全量评论、弹幕、完整转写、完整性账本、监控、目录和能力进化。

新文档 `2026-08-08-pi-agent-framework-correction-research.md` 明确 Pi 只承担一次有边界的模型—工具循环，SourceOS 继续拥有 PostgreSQL 任务事实、RQ 队列、浏览器、完整性、身份、证据和长期记忆。

产品定位已经确认：

> 自治浏览器研究 Agent 是 SourceOS 的第一台现实感知与数据采集生产引擎，不是整个 SourceOS。

它负责“看见现实”，其产出进入需求、战略、产品、研发、销售、运营和金融引擎。

强项：

- Agent 层泛化、执行层确定；
- 长任务可恢复；
- 完整性由确定性账本证明；
- 未知站点探索路径可以沉淀为可测试能力；
- 能力漂移时回退、修复和升级；
- Pi 与 SourceOS 领域和耐久状态隔离。

需要修正的过载：

- 首个里程碑不应同时交付十二个 Target Pack、二百五十个模板、四十个核心目标、完整身份自治和所有导入导出格式；
- “全量”应限定为正式纳入目标内的可验证全量，不是全网无差别采集；
- 账号注册和凭据自治属于后续能力，不应阻塞第一个 Reality Dataset 闭环；
- 文档中的长期自我进化目前主要是能力选择和漂移修复，还不是代码变异、竞争评测和自动提升。

## 17. 控制论自治公司总体架构

采用的总体路线不是线性 Agent 流水线，也不是中央超级 Agent，而是控制论自治公司：

```text
所有者
→ 经营宪法
→ CEO Engine：战略、机会组合、资源配置
→ 现实感知 / 战略商业 / 产品干预 / 研发生产 / 销售运营 / 金融利润引擎
→ 共同世界模型和经营账本
→ Evolution Kernel
→ 现实世界结果
→ 再校准与再分配
```

每个生产单元通过正式 `Work Contract` 协作，至少包含：目标、委托方、承接方、权威输入、交付物、验收标准、资源上限、权限、期限、预期价值和失败策略。

共同世界模型至少需要表达：Actor、Context、Problem、Behavior、Workaround、Cost、Evidence、Counterevidence、Mechanism、Need Hypothesis、Opportunity、Product Intervention Thesis、Forecast Snapshot、Product、Feature、Channel、Customer、Delivery、Revenue、Cost、Outcome、Agent Capability 和 Evolution Experiment。

## 18. 完整生产闭环

长期目标闭环：

```text
现实探索
→ Reality Dataset
→ 需求机制与机会预测
→ CEO 资源配置
→ 产品干预定义
→ 规格、Issue 与研发
→ 产品或服务
→ 创作、渠道、销售与交付
→ 收入、成本、留存与客户结果
→ 预测校准
→ 引擎和产品自我进化
```

经济价值不是保证每个产品必然成功，而是长期减少错误下注、提高有效信息获取效率、提前识别致命假设、提高高等级机会的真实成功率，并让成功和失败改善下一次资源配置。

## 19. 建设顺序

不能同时开发所有引擎，必须按纵向闭环推进：

1. **现实感知**：自治浏览器研究 Agent、两个参考平台、目标内全量、Reality Dataset、完整性、谱系、恢复和监控；
2. **机会预测**：需求机制、反证、产品干预假设、Forecast Snapshot、信息价值；
3. **产品生产**：规格、Issue、R&D Agent、测试、审查和产品结果回填；
4. **经营闭环**：内容、渠道、销售、交付、成本、收入、利润和 CEO 资源配置；
5. **自主进化**：代码与流程变体、回放基准、竞争评测、自动提升和回滚。

最先必须跑通的纵向链路：

> 一个自然语言研究目标 → Agent 自主探索 → 一份可验证 Reality Dataset → 一个可追溯产品干预假设。

如果这条链不能真实运行，后续 CEO、销售、金融和自我进化只是角色扮演。

## 20. 尚未解决的核心问题

1. 新自治研究 Agent 的默认扩源权限，如何与旧 `Approved Collection Boundary` 决策兼容；
2. 持久化混合模型尚未在 GitHub 决策票中完成；
3. `Product Intervention Thesis`、`Forecast Snapshot` 和事前预测登记尚未进入正式数据模型；
4. Evolution Kernel 的版本、实验、评测、提升、回滚和防评价污染协议尚未写成规格；
5. CEO Engine 的机会组合和资源配置算法尚未定义；
6. 各生产引擎的 Work Contract 和统一成本账本尚未定义；
7. 当前本地主分支与远端严重分叉，尚未形成安全的整合策略；
8. 自治浏览器研究 Agent 的第一里程碑必须重新切小，而不删除长期愿景。

## 21. 后续工作原则

- 不再把采集量、模型活动量、报告数量或功能数量解释为价值；
- 不让同一模型的多轮意见冒充独立证据；
- 不把本体关系自动解释为因果关系；
- 不把强烈抱怨自动解释为支付意愿；
- 不把 SourceOS 与通用模型竞争，Pi 和模型始终是可替换认知供应商；
- 不让所有引擎同时扩张，优先形成一条可运行纵向闭环；
- 不以合规讨论替代产品能力，但也不把账号、信誉、生产数据和外部承诺误认为无风险动作；
- 对产品方向持续进行强对抗审查，证据不足时明确说“不知道”。
