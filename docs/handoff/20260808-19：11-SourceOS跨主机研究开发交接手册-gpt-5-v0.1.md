## 3. 当前最终产品定位

SourceOS 当前不是评论采集工具，也不是单一垂直 Agent。正式定位是：

> SourceOS 是一个受经营宪法约束、以现实结果为选择压力、能够自主感知、决策、生产、经营和进化的控制论一人公司操作系统。

第一台生产引擎是自治浏览器研究 Agent。它负责现实感知、探索、全量深采、转写、完整性、证据谱系、持续监控和 Reality Dataset，不等于整个 SourceOS。

Pi Agent Core 是一次有界认知—工具调用循环，不拥有长期公司状态。PostgreSQL、任务状态机、RQ、浏览器、完整性、证据、身份、长期记忆、经营账本和 Evolution Kernel 由 SourceOS 掌握。

## 4. 已接受的不可重新讨论基础决定

除非出现新的反证，不要在新主机上重新从零争论以下事项：

1. 面向全球、多语言、多地区，不限制单一领域；
2. 系统首先服务用户本人；
3. 评论是重要入口，不是需求、付费或市场规模的充分证明；
4. 采集原则是“自适应广度＋正式目标内全量深采”；
5. 原始材料、证据、解释、判断、Proposal、正式记录和结果必须分离；
6. 通用模型可替换，SourceOS 拥有事实、协议、状态、数据和长期反馈；
7. 长任务由耐久状态机协调多个有界 Agent Run，不维持无限会话；
8. SourceOS 使用 Agent-native 模块化单体，暂不采用微服务和通用图工作流框架；
9. Legal Next Step 使用显式纯函数优先级决策表；
10. 使用事务状态＋不可变事实的混合持久化方向，不做全量事件溯源；
11. 自治浏览器研究 Agent 是第一台现实感知生产引擎；
12. 探索、能力和产品三类自我迭代共用 Evolution Kernel；
13. 允许系统在隔离环境中自主修改工具、Prompt、模型、流程和代码；
14. 长期目标、资源上限、失败审计、所有者终止权不能由参赛版本自行修改；
15. 默认允许无资金消耗、可审计、可停止、可回滚的行动；
16. 资金、重大外部承诺、不可恢复资产操作和宪法修改保留所有者授权；
17. 全局适应度是风险约束下的长期自由现金流、经营者时间收益和生产资产复利；
18. 完整生产闭环是现实探索—需求预测—产品干预—研发—销售交付—经营结果—校准进化。

## 8. 迁移前的安全打包建议

由于当前存在“本地提交＋远端大量新提交＋未提交用户文件＋临时工作树”，不能只复制一个干净 clone。

推荐生成两类迁移物：

### 8.1 Git 对象包

在旧主机项目根目录执行：

```bash
git bundle create sourceos-20260808-all-refs.bundle --all
git bundle verify sourceos-20260808-all-refs.bundle
```

它保存已经提交的本地分支、标签和提交，但不保存工作树未提交文件。

### 8.2 工作树资产包

将项目工作目录另行复制，至少保留：

- 所有未跟踪文档、代码、迁移、测试和原型；
- `.gitignore`、Makefile 与已修改代码；
- 本交接目录；
- 不包含 `.env`、凭据、虚拟环境、缓存、数据库运行数据和 `.superpowers/` 临时视觉会话。

可先生成清单：

```bash
git status --porcelain=v1 > sourceos-20260808-working-tree-status.txt
git diff --binary > sourceos-20260808-tracked-working-tree.patch
git ls-files --others --exclude-standard > sourceos-20260808-untracked-files.txt
```

不要把 `.git/config` 直接复制到新主机。当前远端配置曾包含嵌入式访问凭据；新主机应使用系统凭据管理器或 `gh auth login` 重新配置，并立即轮换任何曾暴露的旧凭据。

## 9. 新主机恢复顺序

1. 安装 Git、GitHub CLI、Python、Node.js、PostgreSQL、Redis 和项目依赖；
2. 使用无嵌入凭据的 GitHub URL clone 远端仓库；
3. `git fetch --all --tags --prune`；
4. 导入或 fetch 本地 bundle 中仅存在于旧主机的 refs；
5. 单独恢复工作树资产包，不覆盖新 clone 的 `.git/`；
6. 保存一份恢复后的 `git status`；
7. 对本地 `main` 的三个提交与最新 `origin/main` 设计独立整合分支，不直接重写 main；
8. checkout `feat/validation-execution-tasks`，核对 PR 120 内容；
9. 读取本交接文件和完整决策沉淀；
10. 在采取任何合并、清理或迁移操作前，先确认所有未跟踪用户文件已经备份。

## 10. 新主机的首个研究任务

不要直接开始实现全部一人公司引擎。推荐按以下顺序恢复研究：

1. 对比最新 `origin/main`、本地三项自治浏览器研究提交和 PR 120；
2. 建立一个安全整合分支，解决文档层的产品定位冲突；
3. 更新 v1.1 决策地图，把本轮新决定纳入路线图；
4. 完成持久化模型票：事务状态＋不可变事实、工作与尝试分离、统一幂等与 Outbox；

7. 之后再拆正式规格和 Issue。

## 11. 迁移后必须继续挑战的问题

- 大规模采集是否真正增加信息，而不是只增加存储；
- 信源是否独立，是否由 AI 合成内容污染；
- 弱关联是否有机制和行动价值；
- 需求是否包含支付、触达和行为改变证据；
- 预测是否在结果发生前冻结；
- 引擎是否用真实经营结果进化；
- 评价标准是否被参赛版本污染；
- 系统是否正在研究成瘾，逃避构建可检验产品；
- 功能是否改善长期自由现金流、经营者时间和生产资产，而不是制造活动量。
